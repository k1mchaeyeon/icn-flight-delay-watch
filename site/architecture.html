인천공항 운항 기록을 같은 기체(등록부호)로 이어 붙여 지연의 시작점과 전이 조건을 분석하는 파이프라인입니다. 자료마다 바뀌는 속도가 달라서 수집 주기를 다르게 두고, 초 단위로 쏟아지는 기체 위치만 스트리밍으로 받습니다.

다음 편 지연 예측

주 1회 재학습합니다. 입력은 앞 편 도착 지연, 여유 시간, 시간대, 날씨, 노선 거리, 항공사입니다. 결과는 predictions/에 저장합니다.

스트리밍 줄의 Lambda는 Kinesis Data Firehose로 보내고, Firehose가 1~5분 또는 일정 용량 단위로 묶어 S3 raw/positions/, raw/events/에 씁니다. 그림에서는 화살표로 줄였습니다. 범위는 인천공항을 거치는 전체 항공사이고, 국내 다른 공항은 비교용입니다.

대시보드가 답할 질문

  1. 그날 지연을 가장 많이 퍼뜨린 노선·편·시간대는 무엇이고, 얼마나 오래 퍼졌나대표 질문. 같은 기체의 연속 운항을 이어 연쇄 길이를 쟽니다 (Glue + Athena)
  2. 지연은 얼마나 많은가연도별 추이와 코로나 전후 비교, 국내선과 국제선 비교 (참고 표 + Athena)
  3. 지연은 어디서 시작되나늦게 뜬 편을 인천 지상에서 새로 생긴 지연과 앞 편에게서 넘겨받은 지연으로 나눔 (Glue에서 기체 잇기)
  4. 어떤 조건에서 다음 편으로 넘어가나지상 여유 시간별 전이율, 날씨 나쁜 날과 좋은 날 비교 (Athena)
  5. 누구에게, 언제 쌓이나항공사·시간대별로 저녁으로 갈수록 커지는지 (Athena)
  6. 오늘 남은 편은 얼마나 늦을까같은 기체 다음 편의 출발 지연 예측 (SageMaker)

왜 이렇게 나눴나

  • 운항 자료는 하루 약 2,400건이라 스트리밍이 필요 없습니다. 정해진 주기로 받는 배치가 싸고 단순합니다.
  • 기체 위치만 초 단위로 쏟아져서 이 줄에만 버퍼링(Firehose)을 둡니다. "왜 파이프라인인가"에 대한 답입니다.
  • Kinesis Data Streams 대신 Firehose를 쓰면 켜 둔 시간이 아니라 들어온 양만큼 과금됩니다.
  • Redshift 대신 Athena: 하루 약 1MB 규모라 켜 둔 시간만큼 과금되는 데이터 웨어하우스보다 조회한 만큼만 내는 Athena가 맞습니다.
  • 원본(raw)과 가공(curated)을 나눠 계산 방식을 바꿔도 원본에서 다시 만들 수 있게 합니다.
  • 인천공항 API는 3일 전까지만 조회되므로, 수집을 먼저 시작해 둔 자료가 과거 데이터가 됩니다.

비용과 보안

  • 비용이 거의 없는 쪽: Lambda, EventBridge, S3, Athena, Glue 크롤러 (하루 수 MB 규모).
  • 비용이 생기는 쪽: Firehose(들어온 양), SageMaker 학습(학습 시간), QuickSight(사용자 수). 웹 대시보드로 대신하면 QuickSight 비용은 없습니다.
  • 보안 기본값: S3 SSE-KMS 암호화, HTTPS만 허용하는 버킷 정책, Lambda·Glue·SageMaker 역할별 최소 권한.
  • API 키: 공공데이터포털 키는 Secrets Manager 또는 Lambda 환경 변수에 두고 코드와 로그에 남기지 않습니다.

월 비용은 아직 요금 계산기로 확인하지 않은 추정입니다. 수집 주기를 확정한 뒤 AWS 요금 계산기로 뽑아 발표 자료에 넣을 예정입니다.
